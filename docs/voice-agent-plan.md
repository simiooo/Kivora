## 0. 一页结论

| 决策 | 结论 | 理由 |
|---|---|---|
| 形态 | 常驻托盘，两个开关：热键模式（默认）/ 常驻模式（可选） | 两个入口对应两种注意力状态，成本与隐私分级 |
| 分工 | **语音层只做调度**，任务在独立会话里跑 | 语音上下文 < 1.5k tokens，延迟与价格都可控 |
| ASR | 四级（L0 唤醒 / L1 短句 / L2 长文 / L3 实时），Voice Director 升降级 | 全云方案，实时全双工单次贵 30–40 倍 |
| 首响 | 语音"加载态"= **预合成 ack 片段**，不占实时通道 | 缓存播报比实时 ack 便宜 600 倍，且更快出声 |
| 实时 | 只保留给"对话与打断"，占比 ≤3% | 3% 时实时仍占单次成本 62%，是唯一要拧的阀门 |
| 上下文 | 6 层上下文栈 + 稳定前缀，前缀命中率目标 ≥ 80% | 只改尾部，不动前缀，吃满 provider 缓存 |
| 权限 | 语音可批 G1/G2，G3 必须屏幕确认 | 防误触、防旁人代答、防电视/音箱误唤醒 |
| 交互 | 取景框 + 虚拟光标 + 4 类轻提示，全部点击透传、不抢焦点 | 不打断用户正在做的事 |

**成本结论（按当前公开价量级估算）**：全实时 $0.097/次 → 分级 $0.0126 → 分级+缓存+ack $0.0047，降 **95%**。
但即使只留 3% 实时，实时仍占单次成本 62%。所以杠杆依旧是"把实时压到 3% 以下"，而"先说一句我在处理"必须用缓存播报，绝不能用实时通道。

## 1. 产品定义

### 1.1 一句话
一个住在 Windows 桌面上的语音助手：你说话，它听懂、拆解、派活，必要时接管鼠标键盘替你把事做完，全程用轻量浮层告诉你它在干什么。

### 1.2 两个开关：热键模式 / 常驻模式

| 模式 | 开关 | 入口 | 预期延迟 | 典型场景 | 计费通道 |
|---|---|---|---|---|---|
| **热键模式**（默认） | 默认开 | `Ctrl+Alt+Space` 按住说 / 单击切换 | < 1.2s | 明确指令："把这个文件发给他" | L1 |
| **常驻模式**（可选） | 默认关，首次开启需显式授权 | 唤醒词"小栗" + 本地 VAD 断句 | < 1.5s | 手不离键盘、连续口述、会议旁听 | L1 / L2 / L3 |

常驻模式的三个护栏：
- **云侧只收到唤醒之后的音频**。唤醒词与 VAD 全在本地，未唤醒的音频不出机器、不落盘。
- 麦克风指示灯常亮；一键"只听不记"（不写 transcript）；30 分钟无交互自动退回热键模式。
- 两种模式共用同一条管线（§2.2），差别只在"谁触发录音"和"是否允许自动升级到 L3"。

### 1.3 边界（第一版不做）
- 不做多人会议纪要（M3 之后）
- 不做跨设备（手机/平板）
- 不做语音克隆、情感 TTS
- 不做无确认的系统级高危操作（装驱动、改注册表、UAC 提权）
- IM 第一版只做"读消息 + 草稿 + 语音确认发送"，不做群聊自动应答

## 2. 总体架构

### 2.1 进程与模块

```
┌──────────────────────────── Windows 桌面 ────────────────────────────┐
│                                                                      │
│  ┌───────────────┐   IPC    ┌──────────────────────────────────────┐  │
│  │  Shell 进程    │◄────────►│  Orchestrator（Node，主进程）          │  │
│  │  Electron 主   │          │  · Session Registry  会话注册表         │  │
│  │  · 托盘/热键   │          │  · Voice Director    升降级判定         │  │
│  │  · 窗口管理    │          │  · Context Assembler 上下文栈组装       │  │
│  └──────┬────────┘          │  · Policy Engine     权限与审计         │  │
│         │                   │  · Cost Router       模型/通道选择      │  │
│  ┌──────▼────────┐          │  · Ack Bank          首响片段库（TTS 缓存）│
│  │ Overlay 渲染   │          └───────┬──────────────┬────────────────┘  │
│  │ 取景框/虚拟光标 │                  │ JSONL RPC    │ JSONL RPC         │
│  │ 提示条/任务卡   │          ┌───────▼──────┐ ┌─────▼────────┐         │
│  └───────────────┘          │ Pi Worker #1 │ │ Pi Worker #2 │  ...    │
│                             │ 任务会话 A    │ │ 任务会话 B    │         │
│  ┌───────────────┐          └───────┬──────┘ └─────┬────────┘         │
│  │ Voice I/O 进程 │                  │              │                  │
│  │ WASAPI 采集    │                  ▼              ▼                  │
│  │ AEC3 + VAD     │          文件系统 / 应用 / 网络 / MCP               │
│  │ 唤醒词 / ASR   │                                                   │
│  │ TTS 播放       │           ┌──────────────────────────┐            │
│  └───────────────┘           │ SQLite：会话索引、审计、缓存 │            │
│                              └──────────────────────────┘            │
└──────────────────────────────────────────────────────────────────────┘
```

**为什么是 Electron**：Pi 内核是 Node/TS，SDK 必须跑在 Node ≥ 22 里；透明置顶窗、点击透传、全局热键、原生音频扩展在 Electron 上都是成熟路径。代价是空载 150–250MB 内存，用"单 Overlay 窗 + 渲染进程休眠"压到 120MB 左右。Tauri 方案要多养一个 Node sidecar，v1 不划算，留给 M2 之后评估。

### 2.2 一次语音指令的时序

```
用户按住热键 / 说唤醒词
  │
  ├─(80ms)   录音开始，本地 VAD 端点检测
  │
  ├─(串流)   ASR partial 到达 ──► 意图预判（不等 final）
  │
  ├─(300ms)  final transcript
  │            │
  │            ├─ A0 反射命中（开应用/切窗口/暂停）──► 直接执行，只出声效
  │            │
  │            └─ 否 ──► 预测任务时长 ──► 选 ack 级别
  │                                    │
  ├─(400ms)  A1 缓存 ack 开始播（"好，我开三个窗口，稍等"）
  │                                    │
  │                                    └─► Voice Brain 生成 dispatcher 调用
  │                                          │
  └─(1.2s)                                   └─► Pi Worker 接活，任务卡出现
                                                │
                                                ├─ 需要权限？──► 语音确认卡 + TTS 提问
                                                │
                                                └─ 完成 ──► 一句话结论 + 卡片变绿
```

三个关键点：
1. **首响不等任务**：ack 在 400ms 内出声，任务在后台跑。
2. **语音层永远不等任务层**：派发完立即回待命，进度靠事件异步回灌。
3. **partial 就开始预判**：省掉 final 之后才决策的那 100–200ms。

### 2.3 会话模型

| | Voice Session | Task Session |
|---|---|---|
| 数量 | 1 个，长期存活 | N 个，按任务创建，完成后归档 |
| 上下文 | < 1.5k tokens（见 §4） | 完整 Pi 会话，自动 compaction |
| 工具 | 6 个调度工具，**无** bash/read/write | 全套 Pi 工具 + MCP + codemode |
| 模型 | 小而快（低延迟档） | 强模型（按任务难度路由） |
| 进程 | 进程内 SDK | 独立 `pi --mode rpc` 子进程 |
| 生命周期 | 随 App | 任务结束 + 24h 归档 |

## 3. 语音通道分层

### 3.1 四级定义（云端 + 用户自配端点）

| 层 | 做什么 | 实现候选 | 延迟 | 单价量级 | 占比目标 |
|---|---|---|---|---|---|
| **L0 唤醒** | 本地关键词 + VAD 门控 | openWakeWord / Porcupine（ONNX，本地） | 常驻 <1% CPU | 0 | 100% 流量 |
| **L1 短句** | ≤15s 单句，热键/唤醒后用 | 云端短音频 ASR（大模型，识别率高） | 300–450ms | $0.006/min | 67% |
| **L2 长文** | 口述、会议、长音频文件 | 云端流式 ASR 分段 + 异步整理 | 首字 400ms，全文滞后 | $0.02/min | 30% |
| **L3 实时** | 全双工、可打断、边说边答 | Realtime API（WebRTC/WS） | 200–400ms | $0.24/min 出 | ≤3% |

选云的理由（已确认）：真正好用的中英混说、抗噪、专有名词识别，本地模型在消费级 Windows 机器上跑不出同等质量；本地只保留"唤醒 + VAD"这两个不需要精度的环节，同时作为隐私闸门。

**端点由用户配置**（v0.4 起）：ASR / TTS / 调度 LLM / 任务模型四段端点全部 BYO，默认 OpenAI 兼容，支持自定义 baseUrl、header 与模型名；产品不代收代付、不做官方账号。

代价与对策：
- 延迟受网络影响 → 选就近区域端点、常连 TLS/WS、ASR 走流式首包（不等整句）。
- 音频出本机 → 明示同意、可关、可设"仅热键模式"；不保存原始音频，只留 transcript（可关）。
- 断网 → 降级为"本地小模型兜底 + 明确告知"，不做静默失败。

### 3.2 L3 的两种用法（重要）

- **L3-A 语音到语音**：模型直接出音频。体验最好，最贵。只给"我们聊聊 / 帮我解释一下 / 我在想……"这类开放式对话。
- **L3-B 实时传输 + 文字大脑**：实时通道只负责 VAD、流式 ASR、打断检测和 TTS 播报，思考仍走文字链路。**价格约为 A 的 1/4，延迟只差 100–150ms**。默认走 B，A 作为"深度对话模式"显式开启。

### 3.3 响应阶梯：先出声，再思考

你的直觉是对的——**首响和答案是两件事**。但"用实时通道回一句我在思考"是最贵的实现方式：实时 ack 单次 $0.011，缓存播报 $0.00002，差 600 倍，而且不会更快（WebSocket 建连 200–500ms，缓存片段 50–120ms）。

所以把"实时"降级成响应阶梯里的一级，而不是 ack 的实现：

| 级 | 何时用 | 实现 | 首响 | 单价 |
|---|---|---|---|---|
| **A0 反射** | 意图明确且任务 <300ms（开应用、切窗口、暂停） | 直接执行 + 短促"嗒"声 + 光环 | <80ms | ~0 |
| **A1 缓存 ack** | 预计任务 0.5–8s | 预合成片段（按意图/语气分类，随音色重生成） | 50–150ms | $0.00002 |
| **A1' 流式 ack** | 缓存未命中，或需要说出具体对象（"我开三个窗口"） | 模板句 + 流式 TTS | 180–300ms | $0.0002 |
| **A2 实时双工** | 对话式追问、需要打断 | L3-B（实时传输 + 文字大脑） | 200–400ms | 高 |
| **A3 语音到语音** | 显式"我们聊聊" | L3-A | 200–400ms | 最高 |

**ack 说不说，按"预测任务时长"决定，不按礼貌**：

| 预测任务时长 | 说什么 | 理由 |
|---|---|---|
| <0.5s | 不说，只出声效 | 说了反而慢 |
| 0.5–2s | "好" / "嗯" | 占位，不喧宾夺主 |
| 2–8s | "我开三个窗口，稍等" | 说出理解的任务，顺带给出纠错窗口 |
| >8s | ack + 5s 时一句"还在弄" | 只补一次，避免话痨 |
| 需要授权 | ack 直接变成问题 | 不浪费一次开口 |

**防"说一句就沉默十秒"**：ack 之后必须有可观测进度（卡片 + 光环），超过 8s 只补一次口头进度。这是体验分水岭。

**ack 片段库怎么建**：按"意图类 × 语气 × 音色"预生成，约 20 类 × 3 语气 ≈ 60 条，随音色切换批量重生成；未命中时走 A1' 模板 + 流式 TTS。片段存本地，播放走内存映射，50ms 内出声。

### 3.4 升降级规则（Voice Director）

| 信号 | 判定 | 动作 |
|---|---|---|
| 祈使句 + 动词开头（打开/关掉/发给/记一下） | 命令 | 走 L1，且优先 A0 反射 |
| 疑问句 + 无明确动词，或"为什么/怎么样/帮我看看" | 对话 | 升 L3-B |
| 用户打断 TTS 两次以上 | 想要双向 | 升 L3-B（本次会话内保持） |
| 连续 2 句命令型 | 回到工单模式 | 降回 L1，关闭实时连接 |
| 20s 无语音 | 空闲 | 关闭 L3 连接，释放计费 |
| 音频 > 15s 且非对话 | 长文 | 转 L2 异步，先回"我记着，稍后整理" |

判定用**规则 + 小分类器**（embedding 最近邻，几十条种子语句即可），不额外调 LLM。

### 3.5 延迟预算（p50 / p95）

| 阶段 | 目标 p50 | 目标 p95 | 手段 |
|---|---|---|---|
| 唤醒→开录 | 80 / 150ms | | 预热音频设备，常开流 |
| 说完→final 文本 | 300 / 600ms | L3 200/400 | 本地 VAD 端点，流式 ASR 尾包 |
| final→首响（ack） | 100 / 250ms | | 缓存片段直出，不等模型 |
| ack→首 token | 250 / 500ms | | 900 tok 稳定前缀 + 预热连接 + 小模型 |
| 首 token→首音 | 180 / 350ms | | 按从句切分 TTS，边生成边播 |
| **端到端（命令）** | **0.6 / 1.1s** | | 全链路并行 + 投机执行 |
| **端到端（对话）** | **0.9 / 1.5s** | | L3-B 流式 |

投机执行：ASR 出 partial 时就开始预取窗口信息、预加载工具、预建 Pi worker；final 一到只剩模型调用。

## 4. 上下文栈与缓存（核心）

### 4.1 原则

1. **前缀必须字节稳定**。任何"会变的东西"都放到尾部，否则缓存全废。
2. **上下文按"层"预算**，不是按需拼装。每层有硬上限，超了就压缩或丢弃。
3. **变化的信息只以"追加"形式进入**，不重排、不回头改。
4. **能缓存的中间产物都落 SQLite**：摘要、窗口快照、TTS 音频、ASR 结果、ack 片段。

### 4.2 六层上下文栈（Voice Brain）

| 层 | 内容 | 预算 | 变更频率 | 缓存 |
|---|---|---|---|---|
| C0 内核 | 人设、回答风格（≤25 字先给结论）、TTS 友好格式、安全边界 | 350 tok | 随版本 | 前缀缓存 |
| C1 工具 | 6 个调度工具的 schema | 450 tok | 随版本 | 前缀缓存 |
| C2 用户 | 称呼、语言、时区、应用别名、默认设备 | 120 tok | 近恒定 | 前缀缓存 |
| C3 卡片 | 活跃会话卡片（id 短码 / 标题 / 状态 / 是否等授权），最多 6 张 | 240 tok | 每轮 | 尾部 |
| C4 情景 | 最近 3 条语音指令 + 结果 | 150 tok | 每轮 | 尾部 |
| C5 当下 | 当前 transcript + 环境胶囊（前台窗口标题、≤80 字选中文本） | 180 tok | 每轮 | 尾部 |

稳定前缀 = C0+C1+C2 ≈ **920 tok**，动态尾部 ≈ **570 tok**。
命中率 80% 时，单次有效输入成本约为全价的 20%–25%。

### 4.3 与"上下文压缩"策略的对应

| 大模型上下文压缩的常用手法 | 我们怎么用 |
|---|---|
| 滑动窗口 | C4 只保留最近 3 条，更早的直接丢 |
| 滚动摘要（rolling summary） | 任务会话用 Pi 的 compaction，摘要模板固定为「目标/已完成/卡点/下一步」 |
| 分层摘要（摘要的摘要） | 会话卡片 = 任务会话摘要再压成 40 tok；详情按需展开 |
| 检索增强（RAG） | 卡片不够时，按 utterance 检索历史会话片段，top-3 注入 C3 之后 |
| 语义缓存 | "打开微信"这类意图直接映射动作，跳过 LLM |
| 前缀/KV 缓存 | C0–C2 稳定 + provider 原生前缀缓存（pi-ai 的 provider 层） |
| 结果缓存 | TTS 文本→音频（常用播报 25% 命中）、ASR 音频指纹（重复口令 10% 命中） |

### 4.4 六类缓存

| 缓存 | 键 | 值 | TTL | 命中目标 |
|---|---|---|---|---|
| P1 前缀缓存 | 工具集哈希 + 版本 | provider 侧 token cache | 5–60min | ≥80% |
| P2 摘要缓存 | session_id + 摘要版本 | 摘要 JSON | 永久，增量更新 | 100% |
| P3 感知缓存 | 窗口句柄 + 标题 + 时间戳 | UIA 树 / 选中文本 / 截图 | 2s | 60% |
| P4 语义缓存 | 归一化意图向量 | 动作 / 会话模板 | 7 天 | 20–25% |
| P5 音频缓存 | 文本哈希 / 音频指纹 | TTS 音频 / transcript | 7 天 | 25% / 10% |
| P6 ack 片段库 | 意图类 + 音色 + 语气 | 预合成音频 | 随音色版本 | 85% |

P3 是最容易被忽略但最值钱的一个：同一窗口连续下指令时，UIA 抓取能省 100–300ms。
P6 是"首响"的命脉：命中即 50ms 出声，未命中才走 A1'。

### 4.5 失效规则（防"缓存骗人"）
- 窗口标题/焦点变化 → 立即失效 P3
- 会话状态变化（等授权、完成、失败）→ 立即失效该卡片，并追加到 C3 尾部
- 工具集版本变化 → 前缀整体失效，重建
- 音色变更 → P6 整体重建
- 用户说"不对/不是这个" → 清空 C4 与 P4 相关条目，避免连续错

## 5. 调度层：语音能对会话做什么

### 5.1 六个工具（Voice Brain 的全部工具面）

| 工具 | 入参 | 回参（截断） | 对应 Pi RPC |
|---|---|---|---|
| `list_sessions` | filter: active/done/all | ≤6 条卡片 | 注册表 + `get_session_stats` |
| `get_session` | id, detail: card/summary/full | 40 / 200 / 全文 tok | `get_last_assistant_text`、`get_entries` |
| `create_session` | prompt, profile | id + 预估时长 | `new_session` + `prompt` |
| `steer_session` | id, instruction | ack | `steer` / `follow_up` |
| `abort_session` | id, reason | ack | `abort` + `clear_queue` |
| `focus_session` | id | 卡片置顶 | 注册表 |

> Pi 的 RPC 已经覆盖了 90%：`new_session / prompt / steer / follow_up / abort / get_state / get_messages / get_session_stats / get_last_assistant_text / get_entries / set_session_name`。我们要补的只有"注册表"和"卡片摘要"。

### 5.2 播报策略（少说话）

| 事件 | 是否播报 | 话术长度 |
|---|---|---|
| 任务创建 | 是（A1/A1'） | ≤10 字："好，我开始弄" |
| 进度 25/50/75% | 否（只更新卡片） | — |
| 需要授权 | 是（阻塞式，见 §7） | ≤25 字 + 选项 |
| 超过 8s | 是，仅一次 | "还在弄，快好了" |
| 失败 | 是 | ≤20 字 + "要我再试一次吗" |
| 完成 | 是 | ≤25 字结论，详情进卡片 |

默认**只报头、尾和卡点**。这是"语音只做总结、派发"的产品化表达。

## 6. 桌面交互层

### 6.1 组件清单

| 组件 | 规格 | 出现时机 | 交互 |
|---|---|---|---|
| 取景框 Focus Box | 2px 圆角框 + 8px 标签，主色 `#4F8CFF`，危险 `#FF5A5F` | 定位到控件/窗口时 | 点击透传，500ms 淡出 |
| 虚拟光标 | 14px 圆点 + 120ms 贝塞尔缓动 + 按下 80ms 缩放 | 需要代替用户点击时 | 点击透传 |
| 状态胶囊 | 右上角 220×32，90% 不透明 | 录音/识别/执行中 | 可点开任务卡 |
| 任务卡 | 右下角 320×auto，最多 3 张堆叠 | 有活跃任务 | 可展开详情、可语音操作 |
| 提示 Toast | 底部居中一行，最多 2 条 | 结果/错误 | 3s 自动消失 |
| 聆听光环 | 屏幕边缘 3px 呼吸光 | 麦克风开启 | 红=录音，蓝=处理中 |

### 6.2 Windows 实现要点

- 覆盖层：`WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW`，永远不进 Alt+Tab，不抢焦点。
- 取景框定位：UI Automation `BoundingRectangle`（物理像素）→ 按 per-monitor DPI 换算；UIA 无结果时退化为窗口截图 + OCR/元素检测。
- 跟随窗口：`SetWinEventHook(EVENT_OBJECT_LOCATIONCHANGE)`，窗口最小化/切虚拟桌面时隐藏。
- 虚拟点击：`SendInput` 绝对坐标；点击前先 `SetForegroundWindow`，失败则用 `AttachThreadInput` 兜底。
- 多显示器：坐标系用虚拟屏幕原点，避免负坐标错位。
- 性能：单 Overlay 窗口 + 局部重绘，空闲 <1% GPU；动画统一 60fps，禁全屏模糊。

### 6.3 设计原则
**不遮挡、不抢焦点、不模态、可忽略**。任何提示 3s 内可消失，任何卡片不挡住用户正在打字的区域（优先右下/右上，避让输入焦点矩形）。

### 6.4 首批场景与应用适配

| 场景 | 主通道 | 难点 | 降级方案 | 优先级 |
|---|---|---|---|---|
| 浏览器（Edge/Chrome） | UIA + 快捷键 + 地址栏 | 自绘页面、跨进程标签 | 键盘流（`Ctrl+L` 输入 URL / 搜索） | P0 |
| 文件资源管理器 | UIA + Shell API | OneDrive 占位、虚拟项 | 路径直达（`Win+R` / 地址栏） | P0 |
| Office（Word/Excel/PowerPoint） | UIA + COM 对象模型 | COM 线程模型、受保护视图、宏安全 | 键盘宏 + 剪贴板 | P0 |
| IDE（VS Code / JetBrains） | 命令面板 + 扩展 API + UIA | 自绘编辑区、多窗口 | `Ctrl+Shift+P` + 命令名 | P1 |
| IM（微信/飞书/钉钉/Slack/Teams） | UIA（多为自绘，弱）+ 剪贴板 + OCR 校验 | 反自动化、发错人不可撤销 | 草稿 + 语音确认收件人 | P1 |

**IM 单独说**：价值极高（"读一下新消息""回他明天下午三点"），但发送是**不可撤销动作**，必须走 G2：先说"发给张伟：明天下午三点，可以吗"，确认后才发送；草稿先落输入框、不直接回车。微信这类强反自动化客户端，UIA 树基本不可用，只能"剪贴板 + 键盘 + OCR 回读校验"，稳定性按 80% 估，失败要能优雅退出而不是乱点。

## 7. 权限：语音怎么介入

### 7.1 风险分级

| 级 | 例子 | 授权方式 | 可回滚 |
|---|---|---|---|
| G0 | 读窗口标题、列会话、检索允许目录 | 自动 | — |
| G1 | 在工作区内写文件、打开应用、起草消息 | 知会 + 3s 撤销窗 | 是 |
| G2 | 删除文件、执行 shell、发网络请求、**发送 IM 消息** | **语音确认 + 随机校验词** | 尽量 |
| G3 | 装软件、UAC 提权、支付、凭据、系统级修改 | **仅屏幕点击**，语音不可单独授权 | 否 |

### 7.2 语音确认协议

```
TTS： "要删掉这 3 个文件，确认的话说'确认 蓝鲸'。"
浮层： 同屏显示文件列表 + diff + 倒计时环
用户： "确认 蓝鲸"        → 通过（可选：绑定设备声纹）
用户： "取消" / 其他      → 拒绝，任务挂起
8s 无响应                 → 卡片高亮，转鼠标可点（不自动通过）
30s 无响应                → 取消任务并播报
```

三个设计点：
1. **随机校验词**（每次不同的双字词）防旁人代答、防"确认"被电视/音箱触发。
2. **语音 + 视觉双通道**：说的时候屏幕上必须有等价信息，避免"说了但没看清"。
3. **G3 永不走语音**：这是产品底线，也是过审和信任的基础。

### 7.3 审计与回滚
- 每次授权落 SQLite：时间、会话、工具、参数摘要、音频指纹、授权方式（语音/点击/自动）、策略版本。
- G1 类操作保留 3s 撤销窗 + 文件快照（小文件内容、路径、mtime）。
- 提供"今天它做了什么"面板，按会话聚合，可一键回滚。

## 8. Pi 内核集成

### 8.1 直接复用

| 能力 | 用法 |
|---|---|
| `pi-ai` | 多 provider、流式、thinking level、成本统计、provider 前缀缓存 |
| agent loop | 任务会话的思考-工具循环，含并行工具、`beforeToolCall` 拦截 |
| session 树 + compaction | 会话分支、回溯、自动摘要（我们只提供摘要模板） |
| 工具集 | read/edit/write/grep/bash（Git Bash）+ `powershell` 工具 |
| MCP | 直接接入用户已有 MCP server（日历、邮件、内部系统） |
| CUA | 不自研：接 **cua-driver**（`cua-driver mcp`），权限用它的 `bounded` + manifest |
| codemode | "一句话办一串事"：让模型写脚本批量调工具，只回结果 |
| extensions | 把权限钩子、审计、播报做成 extension，不 fork 内核 |
| RPC | 会话控制的完整接口面（见 §5.1） |

### 8.2 必须自研

音频采集/回放（WASAPI + AEC3）、VAD、唤醒词、流式 ASR 接入、TTS 与切分、ack 片段库、打断管理、权限引擎与审计、Overlay 渲染、会话注册表、Voice Director、成本路由。应用适配器 MVP 交给 cua-driver，长期再考虑自研 UIA/COM 层。

### 8.3 进程模型

- **Voice Brain**：进程内 SDK 会话（`createAgentSession`，`noTools` + 自定义 6 工具），省一次进程往返。
- **Task Session**：独立 `pi --mode rpc` 子进程，预热池 2–4 个，空闲 90s 回收。
- **隔离**：任务进程可用低权限 Windows 用户/受限令牌启动（M2 再做），至少做到"一任务一进程，可单独 kill"。
- **云依赖**：ASR/TTS/LLM 全云；本机只保留唤醒、VAD、Overlay 与调度。断网时明确降级，不静默失败。
- **崩溃**：worker 挂了只影响单个会话，Overlay 卡片变红并提供"重试"。

### 8.4 已知坑
- Pi 无内建权限系统，`project trust` 不是沙箱 → 权限必须做在我们这层。
- Windows 上 `bash` 工具依赖 Git Bash；体验上应默认启 `powershell` 工具并调整 `defaultTools`。
- codemode 默认 2 个 worker，并发高时要设 `PI_CODEMODE_MAX_WORKERS`。
- 会话文件默认在 `~/.pi`，产品化要改到 `%LOCALAPPDATA%\<app>\sessions`。
- 扩展在 RPC 模式下不能渲染自定义终端组件，Overlay 必须由我们自己的渲染层做。

## 9. 成本模型

假设：单次交互 7s 语音、prompt 1400 tok（其中 900 稳定前缀）、输出 120 tok、TTS 120 字、ack 8 字；实时会话按 25s 入 + 18s 出计费。单价为量级占位（见 `cost_model.py`，换价即算）。

| 方案 | $/次 | 典型用户 40 次/天 · $/月 | 重度 200 次/天 · $/月 |
|---|---|---|---|
| A 全实时 | 0.0970 | 85.36 | 426.80 |
| B 分级，3% 实时，无缓存 | 0.0126 | 11.05 | 55.27 |
| C 分级 + 缓存 + 缓存 ack | 0.0047 | 4.14 | 20.68 |

- 相对 A：B 省 87%，C 省 **95%**；C 相对 B 再省 63%。
- 实时占比敏感性（C 方案，典型用户 $/月）：0% → 1.62；3% → 4.14；5% → 5.81；10% → 10.00；20% → 18.37。
- 3% 实时时，实时仍占单次成本 **62%**（$0.0029 / $0.0047）。
- 首响方式对比：缓存 ack $0.00002/次 vs 实时 ack $0.011/次（**611 倍**）；每月 4400 次 acks：$0.08 vs $48.40。

四条结论：
1. 想压价，先压实时占比（3% 是甜点），而不是优化文字链路那几分钱。
2. "先说一句我在处理"必须是缓存/模板 TTS，用实时通道做 ack 等于把最贵的一档用在了最没价值的一句话上。
3. 前缀缓存是文字链路唯一的大杠杆（80% 命中 ≈ 输入成本降到 1/4）。
4. 若定价 ¥30/月，典型用户毛利健康；重度用户需要配额或降级（如"实时模式每日 10 分钟"）。

## 11. 风险与未决

| 风险 | 影响 | 缓解 |
|---|---|---|
| 云端 ASR/TTS 延迟抖动 | 首响不稳定 | 多供应商热备 + 区域就近 + 本地 ack 片段兜底 |
| 实时价格波动 | 成本模型失效 | 参数化 + 每日成本埋点 + 供应商可切换 |
| UIA 覆盖率不足（自绘 UI、游戏） | 取景框定位失败 | 视觉兜底 + 明确"不支持"边界 |
| IM 反自动化（微信） | 稳定性差、封号风险 | 只做读+草稿+确认；失败优雅退出；不做批量 |
| 语音误唤醒/误确认 | 安全事故 | 校验词 + G3 仅点击 + 设备声纹可选 |
| Electron 内存占用 | 常驻体验差 | 单窗 + 休眠 + M3 评估 Tauri |
| Pi 上游破坏性变更 | 升级成本 | 钉版本 + 只依赖 RPC/SDK 公开面 |

**仍需你确认**：
1. IM 具体是哪几个？（微信 / 飞书 / 钉钉 / Slack / Teams 优先级不同，适配成本差 3 倍）
2. Office 版本范围（2019 / 2021 / 365；COM 可用性不同）与是否需要 WPS。
3. 实时模式的配额策略（每日分钟数 / 会员权益 / 完全不限）。
4. 常驻模式的默认值最终定稿：默认关，还是首启引导用户选一次。
